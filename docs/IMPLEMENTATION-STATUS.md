# وضعیت واقعی پیاده‌سازی اهداف حسابداری آفلاین پادناکِشت

این سند معیارهای هدف را از شواهد پیاده‌سازی و آزمون جدا می‌کند. سبز بودن CI به‌تنهایی به معنی تکمیل محصول یا تأیید انتشار نیست.

## وضعیت فعلیِ تأییدشده

- [x] رابط فارسی RTL و اجرای بسته‌شده در APK آفلاین.
- [x] ماژول قواعد کسب‌وکار با مبالغ صحیح ریال، فاکتور چندقلمی، پرداخت جزئی و محاسبهٔ تغییر موجودی.
- [x] ذخیره‌سازی محلی با افزونهٔ SQLite رمزگذاری‌شده در مسیر Android؛ مسیر وب/مرورگر همچنان از localStorage استفاده می‌کند و نباید با ذخیره‌سازی امن Android اشتباه گرفته شود.
- [x] قفل PIN محلی با مشتق‌سازی PBKDF2-SHA256؛ این قابلیت به‌تنهایی معادل BiometricPrompt یا احراز هویت چندمرحله‌ای نیست.
- [x] پشتیبان‌گیری/بازیابی JSON با اعتبارسنجی، خروجی XLSX و مسیر چاپ/ذخیرهٔ PDF.
- [x] گزارش فروش، حساب مشتری، انبار، مطالبات و هشدارهای محلی.
- [x] تحلیل آفلاین شفاف: برآورد سادهٔ فروش ۳۰ روز آینده از میانگین فروش ۹۰ روز اخیر، مطالبات سررسیدشده، کالاهای کم‌موجودی، و پیشنهادهای مبتنی بر قواعد. این یک مدل آموزش‌دیدهٔ TensorFlow Lite/ONNX نیست و UI همین محدودیت را اعلام می‌کند.
- [x] آزمون‌های خودکار منبع و ساخت وب موفق در اجرای ثبت‌شده.
- [x] ساخت APK آزمایشی، نصب روی شبیه‌ساز Android API 34، اجرای برنامه، بررسی وجود فایل SQLite، فعال‌کردن حالت پرواز، اجرای مجدد آفلاین و بررسی نشانه‌های خطای runtime موفق در اجرای ثبت‌شده: https://github.com/hamedbenapart69-byte/PadnaKesht-App/actions/runs/39459522305

## آخرین شاهد اجرایی ثبت‌شده

- اجرای QA روی commit `fd03b0d2a6ed8c0270fbd2896f49cd9eb6488bd9` در ۲۰ اکتبر ۲۰۲۶ با موفقیت تمام شد: آزمون‌های Node، ساخت دارایی‌های وب، ساخت APK آزمایشی، کنترل checksum، نصب و اجرای APK روی شبیه‌ساز، وجود فایل SQLite، فعال‌سازی تأییدشدهٔ حالت پرواز و اجرای مجدد برنامه در حالت آفلاین.
- گزارش اجرا: https://github.com/hamedbenapart69-byte/PadnaKesht-App/actions/runs/39462569232
- خروجی قابل دریافت از بخش Artifacts همان اجرا با نام `PadnaKesht-QA-Candidate-not-production-approved` است. این خروجی **نامزد QA** است، نه نسخهٔ تولیدی تأییدشده.
- این آزمون وجود فایل پایگاه داده و زنده‌ماندن برنامه را بررسی می‌کند؛ به‌تنهایی رمزنگاری واقعی دیتابیس، دوام یک رکورد واقعی پس از راه‌اندازی مجدد، صحت کامل همهٔ گردش‌های مالی یا سازگاری با گوشی فیزیکی را اثبات نمی‌کند.

## شکاف‌های مهم در برابر اهداف مصوب

- [ ] **Kotlin + Jetpack Compose + Material 3:** پروژهٔ فعلی UI مبتنی بر HTML/CSS/JavaScript در Capacitor است؛ در مخزن شاخهٔ هدف فایل Kotlin ثبت‌شده‌ای وجود ندارد. بنابراین مهاجرت به Compose انجام‌شده محسوب نمی‌شود.
- [ ] **MVVM + Clean Architecture بومی:** لایه‌های native مستقل data/domain/ui، ViewModel و use caseهای Kotlin هنوز پیاده‌سازی نشده‌اند. ماژول JavaScript مربوط به قواعد دامنه یک جداسازی محدود است، نه تحقق معماری بومی.
- [ ] **Room:** ذخیره‌سازی فعلی Android بر پایهٔ افزونهٔ SQLite است، نه Room. مهاجرت به Room نیازمند طرح مهاجرت داده و حفظ داده‌های نصب قبلی است؛ نباید با تعویض دیتابیس، اطلاعات کاربر از بین برود.
- [ ] **BiometricPrompt و AES/SQLCipher با چرخهٔ کلید بررسی‌شده:** قفل PIN و رمزگذاری SQLite موجودند، اما اثرانگشت/چهره و بازبینی مستقل چرخهٔ کلید هنوز تأیید نشده‌اند.
- [ ] **نمودارهای تعاملی کامل Pie/Line/Bar:** نمودار میله‌ای فروش موجود است؛ مجموعهٔ کامل نمودارهای تعاملی بومی Compose هنوز موجود نیست.
- [ ] **TensorFlow Lite/ONNX:** هنوز مدل آموزش‌دیده و آزمون کیفیت پیش‌بینی وجود ندارد؛ خروجی فعلی برآورد آماری شفاف است.
- [ ] **دسته‌بندی خودکار تراکنش با NLP:** هنوز در گردش ثبت دادهٔ اصلی پیاده‌سازی نشده است.
- [ ] **Coroutines + Flow و Paging/LazyColumn:** در برنامهٔ JavaScript فعلی معادل بومی Kotlin وجود ندارد.
- [ ] **JUnit/Espresso/Compose UI tests:** آزمون‌های Node و smoke test شبیه‌ساز وجود دارند؛ این‌ها جای آزمون‌های JUnit و Espresso/Compose را نمی‌گیرند.
- [ ] **اعتبارسنجی روی گوشی واقعی:** نصب، بازشدن، قفل، حفظ داده، اعلان، PDF/XLSX و حالت پرواز باید روی دستگاه فیزیکی نیز آزموده شود.
- [ ] **سوابق واقعی مشتری و فاکتور:** در مخزن دادهٔ واقعی کسب‌وکار وجود ندارد. تا زمانی که فایل پشتیبان معتبر یا دادهٔ نسخهٔ قبلی بازیابی نشده، نباید رکورد ساختگی وارد شود.

## معیار تکمیل واقعی

1. طراحی و اجرای مهاجرت بومی باید با طرح حفظ/انتقال داده همراه باشد؛ نسخهٔ فعلی کاربر نباید بی‌دلیل حذف یا بازنویسی داده شود.
2. همهٔ عملیات مالی با تست‌های واحد و یکپارچه و سناریوهای اصلاح/لغو، پرداخت جزئی، برگشت موجودی و ثبت تکراری پوشش داده شوند.
3. حفاظت کلید و داده، PIN و BiometricPrompt روی Android آزمایش شوند.
4. گزارش‌ها و نمودارها فقط از دادهٔ واقعی استفاده کنند؛ کیفیت پیش‌بینی با معیار عددی و تاریخچهٔ کافی سنجیده شود.
5. APK قابل نصب روی گوشی واقعی، کار در حالت پرواز و دوام داده پس از بستن/اجرای مجدد تأیید شود.
6. ماتریس پذیرش و دروازهٔ انتشار فقط با شواهد واقعی PASS شوند. APK آزمایشی با نسخهٔ نهایی تأییدشده یکسان نیست.
